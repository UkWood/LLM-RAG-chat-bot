## 3. Main findings

1. systems contains both engineering systems and catalog categories; current source has 12 category records and 13 system records.
2. Software is stored in products, not a separate collection.
3. Several relation fields were generated by title mentions, legacy links or title-pattern heuristics. Their presence does not prove engineering compatibility or applicability.
4. inputs/outputs projections can conflict with source values; two conflicts are recorded in the migration report.
5. Schema defaults must not be mistaken for explicit source assertions.
6. Support Catalog is metadata-only. The existing document search does not index PDF text.
7. Some migration reports/scripts are stale relative to current frontmatter; current pinned records and schema are authoritative.
8. industries.yaml is explicitly preliminary.

## 4. Proposed architectural follow-up

Prepared proposed [ADR-0013](../decisions/0013-saturn-relation-provenance.md) to distinguish source approval from semantic review and to prevent heuristic mention links from becoming technical claims.

No coding should begin until the owner approves:
- relation provenance classes;
- System vs Category semantics;
- raw field vs schema-default handling;
- answer eligibility of unreviewed relations;
- whether the initial pilot should use direct product/system facts and separately approved PDF passages while leaving heuristic relations out of answer generation.

## 5. Verification and limitations

This stage was a source/schema inspection, not a runtime test:
- Astro build was not run;
- npm run check:content was not run;
- no PDFs were fetched or parsed;
- no field coverage was recomputed by executing migration scripts;
- no relations were reviewed by a Saturn engineer.

The reports in the source repository are treated as historical evidence about migration methods, not as semantic approval.
