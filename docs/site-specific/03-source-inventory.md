## 1. Структура контента

В текущем snapshot обнаружены следующие Markdown-коллекции:

| Коллекция | Число файлов | Роль |
|---|---:|---|
| products | 292 | изделия и оборудование |
| systems | 25 | системы и каталоговые категории |
| groups | 23 | группы каталога |
| articles | 36 | информационные и технические статьи |
| news | 22 | новости |
| pages | 40 | информационные страницы и типовые решения |

Это количество файлов в репозитории, не число одобренных AI-источников. У записей есть draft; для импорта нужно проверять реальную схему и конкретный snapshot, а не только количество файлов.

Схема коллекций определена в src/content.config.ts. Основные словари: src/data/interfaces.yaml, protocols.yaml, synonyms.yaml, applications.yaml, io-kinds.yaml, spec-names.yaml, а также словари отраслей и порядка вывода.

### 1.1. Изделия

Схема products содержит:
- title — обозначение;
- name — полное наименование;
- article;
- group, systems;
- status (active, obsolete, discontinued) и notice;
- interfaces, protocols, ip, temperature_c, mass_kg, dimensions_mm, lifetime_years, power;
- specs, inputs, outputs, features, connectors;
- documents, certificates, videos;
- related, variant_of, software, articles, solutions;
- Markdown body, legacyId, oldUrl.

Важное следствие: характеристики доступны в двух формах — канонические поля и строки specs. При импорте нельзя терять исходный текст, единицы, условия и связь с исходным полем.

### 1.2. Системы и категории

systems.kind различает system и category. Категория — это каталоговый раздел, а не инженерная система. У системы есть summary, applications, documents, articles, solutions и текстовое описание.

Состав системы строится из обратных ссылок products.systems; отдельное поле состава в записи системы не является единственным источником истины.

### 1.3. ПО, статьи и решения

Программное обеспечение хранится как записи products, обычно в группе «Программное обеспечение», а не как отдельная Astro-коллекция. Статьи связываются с изделиями и системами. Типовые решения — страницы pages с kind=solution, которые могут ссылаться на изделия и системы.

Связи должны импортироваться из явных полей. Нельзя делать вывод «совместимо» только потому, что два изделия упомянуты в одной статье или принадлежат одной системе.

## 2. Поиск №1 — поиск по страницам сайта

Маршрут: /search/.  
Статический индекс: /search-index.json.  
Клиентский движок: MiniSearch (src/lib/search/engine.js, src/lib/search/client.js).

Поиск охватывает:
- изделия: обозначение, наименование, артикул, группу, системы, интерфейсы, протоколы, входы/выходы, IP, характеристики, функции, названия документов и текст страницы;
- системы: название, краткое описание, области применения, названия документов и текст;
- статьи, новости, группы и часть информационных страниц/типовых решений.

В индекс включаются только записи, прошедшие фильтр draft=false; страницы-разделы исключаются, главная формируется отдельно. Для тела контента используются ограниченные plain-text фрагменты.

Механика выдачи приоритизирует совпадение с названием/обозначением, затем заголовки и поля, затем текст. Поиск строгий: fuzzy отключён; для обозначений есть специальные prefix-поведения. Есть нормализация вариантов написания и словарь синонимов, например ИПЛ, БКД, ПЛК.

**Ограничение:** в поле docs попадают названия документов из карточек, а не содержимое PDF. Поэтому поиск по страницам может найти изделие по названию руководства, но не отвечает на вопрос по тексту руководства.

## 3. Поиск №2 — поиск документации раздела «Поддержка»

Маршрут: /service/search/.  
Статический индекс: /doc-index.json.  
Сборка каталога: src/lib/service.ts и src/pages/doc-index.json.ts.  
Поисковый движок: src/lib/doc-search.js.

Каталог формируется из documents и certificates опубликованных записей products и systems. Документы дедуплицируются по URL; к одной записи могут быть привязаны несколько владельцев.

Для документа передаются:
- название (t);
- тип (k) и подпись типа (kl);
- раздел поддержки (s);
- версия (v);
- URL файла (u);
- владельцы (o): название, полное имя, ссылка на карточку, тип владельца.

Типы документов: руководство, программное обеспечение, презентация, сертификат, декларация, реестр, паспорт, скан, прочий документ. Разделы: документация и паспорта; программное обеспечение и загрузки; сертификаты и декларации; каталоги и брошюры.

Поиск использует обозначения изделий/систем, полные наименования и названия документов; поддерживает нормализацию и транслитерацию кириллицы в латиницу. Слова запроса должны находиться в обозначении, наименовании или названии документа; последний набираемый термин может совпадать по префиксу.

**Ограничение:** это поиск по метаданным каталога. Он не скачивает PDF и не индексирует его внутренний текст. Его результат — найти правильный файл и владельца, а не извлечь ответ из страниц документа.

## 4. Старый файловый сервер

Файлы не входят в сборку сайта и не хранятся в репозитории. В карточках присутствуют ссылки на пути вроде /ftp/, /public/, /update/ и другие директории. Функция fileUrl() может добавлять asset origin для preview; при обработке нужно использовать точный итоговый URL, заданный данными и конфигурацией, а не собирать адрес вручную.

Примеры текущих ссылок из карточек:
- БКД-ПК-RF.2 — «Руководство по эксплуатации Контроллер БКД-ПК-RF.2»: https://www.mnppsaturn.ru/ftp/public/doc/bkd-pk-rf2/re%20BKD-PK-RF2.pdf;
- БКД-UPS — «Руководство по эксплуатации контроллера БКД-UPS»: /ftp/public/doc/bkd-ups/re%20bkd-UPS3.pdf;
- СОС-95 — «Руководство по эксплуатации СОС-95»: /ftp/public/doc/sos-95/re%20SOS-95.pdf.

Эти примеры подтверждают наличие ссылок, но не доступность файлов, актуальность редакции, качество извлечения или разрешение на AI-ingestion.

## 6. Рекомендуемая модель источников для RAG

Разделить данные на три типа, не смешивая их происхождение:

| Канал | Содержимое | Цель |
|---|---|---|
| Site content | Markdown/frontmatter/словарные данные | факты, описания, сущности и связи |
| Support catalog | title/kind/version/URL/owners | найти правильный документ и показать ссылку |
| Extracted document | текст PDF, страницы, таблицы, headings | отвечать на вопросы по содержимому документа |

Единый RAG-оркестратор может искать по всем трём каналам. Но source type, revision, access policy и citation format сохраняются отдельно.

## 7. Что не делать

- Не менять поисковые страницы сайта и их JS.
- Не использовать search-index.json или doc-index.json как единственную базу RAG.
- Не считать, что doc-index.json содержит текст PDF.
- Не сканировать весь файловый сервер и не скачивать все найденные ссылки автоматически.
- Не индексировать Old_Site/, SQL dump, PHP-код и служебные файлы.
- Не переносить в RAG произвольные данные только потому, что они доступны в Git.
- Не считать опубликованность и наличие URL подтверждением технической актуальности или разрешения на cloud.

## 8. Вывод аудита

У сайта уже есть хорошая структурированная основа: карточки изделий, отдельные системы, связи, словари, характеристики и каталог документов. Два текущих поиска решают разные задачи: поиск по страницам и поиск файла в каталоге поддержки. Но ни один из них не индексирует полный текст PDF.

Поэтому наиболее прямой путь — сохранить текущие пользовательские поиски без изменений, а в отдельном AI-проекте построить собственные адаптеры к контенту сайта, Support catalog и разрешённым текстам PDF.
