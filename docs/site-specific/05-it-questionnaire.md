# Вопросы для ИТ по техническому консультанту Сатурна

Дата: 2026-11-08  
Назначение: документ для письменного согласования инфраструктуры, доступов и эксплуатации пилота.

## 1. Размещение backend

1. Где предполагается разместить FastAPI backend: на офисном сервере, отдельной VM или другом сервере?
2. Какая ОС и версия доступны?
3. Какие CPU (модель/число ядер), RAM и свободный SSD/HDD доступны?
4. Есть ли возможность выделить отдельную VM/контейнер?
5. Какой лимит диска можно выделить под исходные разрешённые PDF, extracted text, BM25, Qdrant и snapshots?
6. Есть ли требования к резервированию/виртуализации?
7. Есть ли ограничения по Docker/Podman? Если контейнеры запрещены, допустим ли systemd service?

## 2. Сеть и внешний доступ

1. Какой адрес/домен может быть выделен для API? Решение пока не принято; имя не следует резервировать до согласования.
2. Может ли backend быть доступен из Internet по HTTPS?
3. Какой reverse proxy используется (Nginx, Apache, IIS или другой)?
4. Кто выпускает и продлевает TLS-сертификаты?
5. Какие правила firewall применяются для входящих соединений?
6. Разрешён ли исходящий HTTPS из backend к внешнему LLM API?
7. Разрешён ли исходящий HTTPS к домену старого файлового сервера для получения выбранных PDF?
8. Можно ли ограничить доступ к Qdrant только localhost/private network?
9. Можно ли ограничить CORS конкретными origin сайта/виджета?
10. Есть ли WAF, reverse-proxy rate limit или другая защита публичного API?

## 3. Read-only доступ к репозиторию сайта

1. Каким способом AI-проект будет получать точный snapshot UkWood/Saturn-Main-Site?
2. Можно ли выдать отдельный GitHub deploy key/token/GitHub App с правами **Contents: Read-only**?
3. Кто отвечает за выдачу/отзыв этого доступа?
4. Допустимо ли получать snapshot вручную по согласованному commit, без автоматической синхронизации?
5. Подтверждается ли, что никакой write-доступ для консультанта не требуется и не будет запрашиваться?

Требование: доступ к репозиторию сайта должен быть технически ограничен чтением. Никакие операции записи в него не нужны.

## 4. Старый сервер документов

1. Доступны ли ссылки из карточек сайта с сервера, где размещены /ftp, /public, /update и другие каталоги?
2. Есть ли ограничения по IP, User-Agent, TLS, авторизации или частоте запросов?
3. Можно ли скачивать только конкретные файлы по согласованному manifest/allowlist?
4. Есть ли актуальный список редакций руководств и сертификатов?
5. Кто подтверждает, что конкретный файл — действующая редакция?
6. Есть ли сканированные PDF, требующие OCR?
7. Есть ли документы с таблицами/чертежами, для которых извлечение текста может быть неполным?
8. Есть ли ограничения на копирование PDF в локальное хранилище AI-проекта?
9. Можно ли вычислять SHA-256 и хранить локальную рабочую копию только для допущенных документов?

Требование: не выполнять массовый обход старого файлового сервера и не скачивать все найденные ссылки.

## 5. Внешний LLM provider

1. Допускается ли отправка фрагментов публичных документов во внешний API Qwen/Alibaba Cloud Model Studio?
2. Есть ли корпоративные ограничения по стране/региону размещения, retention, обучению моделей на запросах, логированию и обработке данных?
3. Кто утверждает передачу конкретного документа во внешний provider?
4. Может ли provider получать только извлечённые фрагменты, без полного файла и без служебных metadata?
5. Где хранится API key и кто его ротирует?
6. Какой бюджет/лимит запросов допустим на период пилота?
7. Какие endpoint/model/region официально разрешены? Их нужно проверить по актуальной документации провайдера перед настройкой.

Если внешняя передача не разрешена, cloud generation отключается; локальный Fake/test path сохраняется, а локальная LLM рассматривается отдельным этапом.

## 6. Локальные модели и CPU

1. Подтверждается ли, что на первом этапе GPU не предоставляется?
2. Допустима ли локальная CPU-работа embedding/reranker?
3. Какие ограничения по CPU/RAM/latency допустимы для индексации и пользовательского запроса?
4. Разрешена ли загрузка заранее проверенных модельных файлов из Hugging Face или требуется внутренний артефактный registry?
5. Кто проверяет лицензионные условия и происхождение весов перед production?

## 7. Хранилище, backup и восстановление

1. Где хранить approved PDF copies, extracted text, snapshots, BM25 и Qdrant data?
2. Какой режим backup и retention применяется?
3. Как часто нужно сохранять snapshot/index?
4. Есть ли возможность восстановить предыдущий проверенный snapshot после ошибки обновления?
5. Как будет выполняться отзыв источника и очистка его данных из активных индексов/cache?
6. Кто отвечает за контроль свободного места и состояние сервиса?

## 8. Логи и персональные данные

1. Какие сроки хранения логов разрешены?
2. Можно ли хранить текст вопроса пользователя, или достаточно request ID, outcome, latency и source IDs?
3. Нужно ли скрывать/маскировать IP адреса и другие идентификаторы?
4. Кто имеет доступ к диагностическим логам?
5. Какой порядок удаления логов и ротации?

В MVP не планируется пользовательская регистрация, CRM, долговременная память или загрузка пользовательских файлов.

## 9. Эксплуатация и ответственность

1. Кто владелец backend/VM и кто принимает обращения при сбое?
2. Кто отвечает за обновление корпуса и согласование новой редакции источника?
3. Кто имеет право отзывать документ из AI-корпуса?
4. Кто подтверждает качество ответов на технических вопросах?
5. Кто принимает решение о начале публичного пилота?
6. Кто согласует отдельное подключение виджета к сайту после приёмки?

## 10. Что нужно получить по итогам обсуждения

- согласованная схема размещения backend;
- CPU/RAM/disk и ОС;
- адрес API и схема HTTPS;
- входящие/исходящие сетевые правила;
- read-only Git-доступ к snapshot сайта;
- разрешённый способ получения выбранных PDF;
- решение по Qwen Cloud API или запрет внешней передачи;
- правила хранения logs, backups и secrets;
- ответственные за допуск источников, техническую проверку и эксплуатацию.

## 11. Принципиально не требуется для MVP

- SQL Server/PostgreSQL/MySQL;
- публичный доступ к Qdrant;
- write-доступ к Saturn-Main-Site;
- изменение текущего сайта;
- отдельная административная CMS;
- GPU-сервер;
- внутренние закрытые документы;
- CRM или multi-tenant инфраструктура.
