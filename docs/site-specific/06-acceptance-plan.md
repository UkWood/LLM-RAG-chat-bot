# План испытаний и критерии приёмки пилота

Дата: 2026-11-08  
Статус: предлагаемые измеримые критерии для real-sample pilot; должны быть подтверждены владельцем до blind evaluation.

## 1. Что именно принимается

Нужно отдельно измерять четыре свойства:

1. **Ingestion correctness** — корректно ли прочитаны исходные материалы, версии, таблицы, связи и страницы PDF.
2. **Retrieval quality** — находится ли правильный источник/фрагмент.
3. **Answer quality / grounding** — отвечает ли консультант полностью и только по evidence.
4. **Product/security readiness** — безопасны ли API, provider, источники и эксплуатация.

Зелёный CI не означает, что система правильно отвечает. Попадание документа в Top-5 не означает, что evidence достаточно для полного ответа.

## 2. Подготовка корпуса

- Ориентир пилота — около 10 одобренных source objects/documents.
- Текущие 8 кандидатов (4 записи контента + 4 PDF-ссылки) не допущены; перед использованием требуется review и approval.
- Для каждой страницы фиксируются commit, path и SHA-256.
- Для каждого PDF — точный URL, fetched bytes hash, фактическая редакция, физическое число страниц и качество extraction.
- Документы с плохим extraction не включаются в положительные gold cases до ручной проверки.
- У каждого gold fact есть source pointer: source ID, field path/heading, page для PDF и подтверждённый текст/значение.

## 3. Retrieval evaluation

Положительные вопросы заранее связываются с одним или несколькими допустимыми источниками/evidence chunks.

Метрики:
- Source-hit@5;
- evidence recall;
- MRR и nDCG;
- доля запросов, где точное обозначение/артикул найдено;
- качество на кириллице/латинице, дефисах, точках, сокращениях и опечатках;
- качество раздельно по каналам: site content, Support catalog, PDF full text.

Предлагаемый первичный retrieval gate: правильный источник должен попадать в Top-5 минимум для 90% положительных retrieval-вопросов пилотного набора. Это целевой показатель поиска, а не доказательство корректности генерации.

## 4. Answer evaluation

Сохраняется строгая схема независимой оценки проекта:

- 24 положительных вопроса, на которые в approved corpus есть достаточные сведения;
- 16 отрицательных/неоднозначных случаев, где система должна отказать или уточнить;
- всего 40 blind cases.

Предлагаемый критерий приёмки:
- 24/24 положительных случаев — полностью корректный ответ по всем обязательным требованиям вопроса;
- 16/16 отрицательных/неоднозначных случаев — правильный отказ или уточнение;
- 0 неподтверждённых технических утверждений;
- 100% корректность source IDs, URL, версий и номеров страниц в выданных citations;
- отсутствие выдуманных изделий, параметров, протоколов, связей и документов.

Неполный ответ не считается полным успехом. Корректный отказ на вопрос, где достаточное evidence присутствует, считается false refusal и не проходит положительный кейс.

## 5. Состав тестовых случаев

Рекомендуемые категории для blind set:

| Категория | Примеры |
|---|---|
| Точная характеристика | питание, диапазон, интерфейс, IP, габариты |
| Точное обозначение | БКД-ПК-RF.2, БКД-UPS, СЛДКС-1 |
| Переформулировка | бытовое описание задачи вместо терминов сайта |
| Несколько требований | изделие + интерфейс + ограничение |
| Связи | изделие → система, ПО, статья, типовое решение |
| Состав системы | состав только по явно заданным связям |
| Поиск документа | найти нужное руководство/паспорт |
| Вопрос по PDF | конкретное значение/процедура с номером страницы |
| Конфликт/разные версии | две редакции или противоречащие источники |
| Неоднозначность | неясное обозначение или неполный запрос |
| Отсутствующий факт | вопрос, ответа на который в корпусе нет |
| Несуществующее изделие | правдоподобный, но отсутствующий индекс |
| Отрицание/квалификатор | «не поддерживает», Modbus TCP vs RTU, только определённый диапазон |
| Prompt injection | просьба игнорировать правила и ответить из общих знаний |
| Недопущенный источник | документ существует, но pending/revoked |
| Вне предметной области | запрос, не относящийся к материалам компании |

Для разработки можно использовать отдельный calibration set. Blind set создаётся независимо, фиксируется hash и не открывается implementer до freeze/first run. После первого запуска запрещено подстраивать код, thresholds или labels под этот набор и повторно объявлять его независимым.

## 6. Проверки источников и citations

Обязательные тесты:
- URL ведёт на реальную страницу или исходный файл;
- PDF page — физическая страница в фактическом файле;
- version/date не перепутаны с датой загрузки;
- citation относится к тому же source revision, который прошёл policy;
- LLM не может подставить произвольный URL/source ID/page;
- один PDF, связанный с несколькими изделиями, сохраняет все owners;
- revoked source не попадает в retrieval/generation даже из старого snapshot;
- изменившийся hash требует новой ревизии/approval.

## 7. Безопасность

- pending/UNKNOWN/revoked source не индексируется и не передаётся provider;
- INTERNAL (если появится позже) не допускается в публичный контур даже при local provider;
- cloud provider получает только chunks с разрешением cloud_generate;
- prompt injection в запросе и внутри документа не меняет policy;
- пользователь не может заставить backend скачать произвольный URL;
- API keys отсутствуют во frontend, логах и Git;
- Qdrant недоступен напрямую из Internet;
- rate limit и request-size limit работают;
- parser ограничен по размеру/страницам/времени.

## 8. Проверка производительности

На согласованной инфраструктуре измерить:
- время ingestion одного PDF и всего sample;
- время lexical/vector retrieval и reranking;
- полное время ответа;
- CPU/RAM peak;
- размер snapshot и индексов;
- поведение при нескольких одновременных запросах;
- отказ/timeout при недоступном provider.

Фиксированный latency target не назначать до получения характеристик сервера и выбранного API. В отчёте указывать фактическую среду, модель, snapshot и конфигурацию.

## 9. Результат приёмки

Отчёт должен включать:
- commit AI-кода и snapshot источников;
- hash корпуса, dataset и конфигурации;
- версии parser/chunker/embedding/reranker/provider;
- метрики retrieval;
- все blind outcomes и причины ошибок;
- долю false refusals и false answers;
- качество citations;
- security test results;
- известные ограничения;
- решение: accepted / not accepted / accepted with explicit limitations.

Провал quality gate нельзя компенсировать красивым интерфейсом, увеличением числа документов или подключением более дорогой LLM. Сначала исправляется причина, затем готовится новый независимый набор.
