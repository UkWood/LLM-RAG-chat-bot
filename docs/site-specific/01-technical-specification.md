# Техническое задание v0.1
## Технический AI-консультант сайта ООО «МНПП Сатурн»

Дата: 2026-11-08  
Статус: проект ТЗ для рассмотрения и уточнения владельцем проекта и техническим специалистом.

## 1. Назначение

Создать отдельный технический чат-консультант для посетителей сайта МНПП «Сатурн». Система должна помогать прежде всего инженеру-проектировщику, а также техническим специалистам и руководителям заказчиков находить подтверждённые сведения об оборудовании, системах, программном обеспечении, типовых решениях и технической документации компании.

Консультант не является универсальным ChatGPT. Он не должен восполнять пробелы собственными знаниями модели, угадывать характеристики или выводить совместимость по аналогии.

**Основной принцип:** каждое техническое утверждение в ответе должно опираться на разрешённый источник из контролируемой базы знаний. При недостатке доказательств система задаёт уточняющий вопрос либо отказывается от содержательного ответа.

## 2. Целевая аудитория и основные сценарии

Приоритетная аудитория — инженер-проектировщик. Дополнительная — технический специалист и руководитель заказчика.

Система должна поддерживать следующие сценарии:

1. Найти устройство по обозначению, полному названию или назначению.
2. Получить подтверждённые характеристики: интерфейсы, протоколы, питание, диапазоны, входы/выходы, габариты и другие опубликованные параметры.
3. Узнать, в каких системах применяется изделие, и какие изделия явно связаны с системой.
4. Найти совместимое программное обеспечение, статьи и примеры применения, если эти связи явно заданы в источниках.
5. Найти типовое решение по описанию инженерной задачи и показать связанные системы/изделия.
6. Найти руководство, паспорт, сертификат, декларацию, презентацию или программное обеспечение.
7. Ответить на вопрос по содержимому разрешённого PDF с указанием страницы и ссылки на оригинал.
8. Сравнить два изделия или решения только по сопоставимым опубликованным параметрам.
9. Попросить уточнение, если обозначение, объект или требуемый параметр неоднозначны.
10. Отказаться, если нужных сведений нет, источник не разрешён, документы недоступны или найденные материалы противоречат друг другу.

Примеры вопросов:

- «Как организовать передачу показаний теплосчётчиков с удалённых объектов?»
- «Какие интерфейсы поддерживает БКД-ПК-RF.2?»
- «В каких системах применяется БКД-UPS?»
- «Какие компоненты входят в СОС-95?»
- «Найдите руководство по эксплуатации СЛДКС-1».
- «Чем отличаются два контроллера по питанию и интерфейсам?»

## 3. Границы проекта

### 3.1. Обязательные ограничения

- Репозиторий UkWood/Saturn-Main-Site используется только для чтения. Запрещены любые изменения исходников, данных, конфигурации, workflow, URL, assets, веток и Git-истории.
- Разработка ведётся в отдельном репозитории UkWood/LLM-RAG-chat-bot.
- Консультант имеет собственные ingestion, индексы, API и интерфейс.
- Существующие поиски сайта сохраняются без изменений.
- Для первой версии используется только явно допущенная публичная информация.
- Содержимое PDF должно быть отдельно проверено и допущено; ссылка на PDF в карточке изделия не является разрешением на загрузку, индексацию или отправку в облако.
- Не индексировать автоматически весь старый файловый сервер.
- Не включать Old_Site/, дампы БД, служебные документы репозитория, скрипты, код и настройки сайта в пользовательскую базу знаний.
- Внешний LLM-провайдер получает только фрагменты, явно разрешённые для cloud generation.

### 3.2. Объём MVP

Первый реальный пилотный корпус — ориентировочно 10 источников/документов, отобранных и проверенных совместно с техническим специалистом. В текущем реестре AI-проекта уже есть 4 кандидата из Markdown-контента и 4 ссылки на PDF; все восемь находятся в статусе UNKNOWN/pending и не разрешены для чтения/индексации/облачной передачи.

В MVP входят:

- read-only импорт выбранных Markdown/YAML/JSON-данных сайта;
- каталог документов из карточек изделий и систем;
- загрузка и обработка только явно допущенных PDF;
- собственный hybrid retrieval;
- evidence gate, citations и корректный отказ;
- сменный LLM provider;
- минимальный самостоятельный web-интерфейс;
- тестовый и диагностический режим;
- измерение качества на реальном пилотном корпусе.

### 3.3. Не входит в MVP

- изменение сайта или его репозитория;
- автоматическое индексирование всего сайта и всех файлов старого сервера;
- закрытая INTERNAL-база и внутренний чат для сотрудников;
- административная CMS/панель управления контентом;
- пользовательская регистрация и личные кабинеты;
- CRM, заявки, заказы и коммерческие операции;
- multi-tenant;
- загрузка произвольных файлов посетителями;
- автономные агенты, управление оборудованием или выполнение команд;
- fine-tuning модели;
- голосовой интерфейс;
- долговременная память о пользователях;
- сложная аналитическая платформа.

Интеграция виджета непосредственно в публичный сайт рассматривается отдельным этапом после приёмки пилота. Поставляемый виджет должен быть самостоятельным артефактом AI-проекта; внедрение выполняется владельцем сайта отдельно и не предполагает правок репозитория сайта в рамках данного проекта.

## 4. Функциональные требования

### FR-01. Импорт контента сайта

Импортировать только выбранные записи из коллекций products, systems, groups, articles, news, pages и необходимые словари из src/data/. Импорт выполняется из зафиксированного read-only snapshot/commit.

Для каждой записи сохранять стабильный ID, тип сущности, заголовок, canonical URL, исходный путь, commit, hash, статус публикации и provenance.

### FR-02. Структурированные характеристики

Характеристики изделия должны индексироваться как отдельные доказательные факты с сохранением:
- имени характеристики;
- значения и единиц измерения, если они есть;
- исходного поля/строки;
- ID изделия;
- статуса изделия;
- source revision.

Не преобразовывать строковые значения в числа без проверяемого правила. Не терять слова «не более», «не менее», знаки допуска, диапазоны и условия применения.

### FR-03. Связи между сущностями

Поддержать явные связи:
- изделие → система;
- изделие → группа;
- изделие → совместимое ПО;
- изделие → связанное изделие/исполнение;
- изделие → статья/типовое решение;
- система → статья/типовое решение;
- типовое решение → системы/изделия.

Для каждой связи хранить тип, направление и происхождение (исходный файл и поле). Не выводить совместимость из одного лишь факта нахождения изделий в одной системе или группе. Не трактовать systems.kind=category как техническую систему.

### FR-04. Каталог поддержки

Импортировать метаданные документов из documents и certificates опубликованных карточек изделий и систем. Сохранять название, тип, версию/дату, URL, раздел поддержки и все связанные изделия/системы.

Один URL может быть связан с несколькими сущностями. Дедупликация файла не должна терять список владельцев и происхождение связей.

### FR-05. Полнотекстовое содержимое документов

После отдельного допуска получать документ по точному URL из каталога, проверять хост и тип содержимого, вычислять SHA-256, фиксировать физическое число страниц и извлекать текст. Для PDF сохранять страницу, заголовок/раздел и структуру таблиц, насколько это возможно.

Сканы и документы с низким качеством извлечения должны маркироваться как требующие OCR/ручной проверки. Не использовать ненадёжно извлечённый текст как доказательство технического ответа.

### FR-06. Независимый поиск RAG

Создать собственные lexical/BM25 и semantic/vector индексы. Использовать гибридное объединение результатов и локальный reranker. Точные обозначения, аббревиатуры, латиница/кириллица, дефисы и цифровые индексы должны иметь приоритетную обработку.

Текущие браузерные индексы сайта не являются поисковым backend консультанта и не должны выдаваться за полнотекстовый индекс PDF.

### FR-07. Единый запрос, раздельные каналы источников

Один вопрос может запускать поиск по трём связанным каналам:
1. структурированный контент страниц сайта;
2. метаданные каталога «Поддержка»;
3. текст разрешённых PDF/документов.

Каналы сохраняют собственные типы источников, metadata и правила цитирования. Оркестратор объединяет кандидатов, но не теряет происхождение результата.

### FR-08. Ответ и уточнение

Ответ должен быть кратким, технически аккуратным и соответствовать вопросу. При неоднозначности система задаёт конкретный уточняющий вопрос. При достаточных данных — отвечает по найденным доказательствам. При недостатке evidence — отказывает.

### FR-09. Цитирование

Backend формирует ссылки и подписи источников. Для страницы показываются название и ссылка на страницу. Для PDF — название, версия/дата при наличии, физическая страница и ссылка на оригинальный файл. Модель не создаёт URL, номера страниц и source IDs самостоятельно.

### FR-10. Контроль фактов

Каждое техническое утверждение должно иметь ссылку на supporting evidence. Проверять существование source/chunk IDs, соответствие snapshot и актуальность policy. При конфликте источников не выбирать произвольно «самый вероятный» вариант: показать конфликт либо запросить проверку.

### FR-11. Статусы изделий

Учитывать active, obsolete, discontinued и notice. В ответе явно указывать ограничения/статус, если они относятся к вопросу. Не рекомендовать снятое с производства изделие как действующее решение без оговорки из источника.

### FR-12. Минимальный интерфейс

На первом этапе — одна строка ввода, отправка вопроса, текст ответа и список источников. Допускаются состояния «уточните вопрос», «недостаточно данных» и «сервис временно недоступен». Интерфейс не должен содержать административных функций.

### FR-13. Диагностический режим

Для разработчика показывать:
- нормализованный запрос;
- retrieval candidates;
- lexical/vector ranks и scores;
- результат fusion/reranking;
- выбранные evidence;
- reason code ответа/отказа;
- использованные snapshot и policy revision.

Не показывать посетителю внутренние scores как вероятность истинности.

## 5. Политика источников и безопасность

Каждый источник получает отдельное решение допуска. Минимальные поля:
- visibility: UNKNOWN / PUBLIC / INTERNAL;
- approval_state: pending / approved / revoked;
- approved_content_sha256;
- approval_id, approved_by, approved_at;
- allowed_usage: local_index, local_generate, cloud_generate;
- cloud_allowed.

По умолчанию доступ запрещён. Изменение bytes/commit создаёт новую ревизию, которая требует повторного допуска. Допуск карточки не наследуется PDF, сертификатом или вложенным файлом.

Qdrant не должен быть доступен из Internet. API key модели хранится только на backend. Обязательны HTTPS, timeout, ограничения размера запросов, rate limiting, CORS allowlist, безопасное логирование, защита от prompt injection и запрет произвольной загрузки URL.

## 6. LLM и модели

Генеративная модель отделяется интерфейсом provider. Первый кандидат — Qwen через проверенный OpenAI-compatible API; конкретный endpoint, модель, регион, тариф и условия обработки данных проверяются до подключения. Конфигурация через LLM_PROVIDER, LLM_BASE_URL, LLM_API_KEY, LLM_MODEL.

В перспективе генеративный провайдер должен заменяться на локальный Qwen/llama.cpp или другой OpenAI-compatible inference endpoint без изменения формата KB, retrieval, citations и frontend.

Embeddings и reranker остаются локальными. В первой версии целевой режим — CPU-only, без обязательного GPU. Выбор модели embeddings фиксируется в snapshot manifest; смена embedding-модели требует переиндексации.

## 7. Данные и развёртывание

На пилоте не требуется отдельная SQL-СУБД. Реестр, manifests и экспорт знаний могут храниться в JSON/JSONL; локальные индексы и snapshot — в файловом хранилище и локальном Qdrant. Qdrant не публикуется наружу.

Сайт остаётся статическим и работает независимо. Backend консультанта разворачивается отдельно за HTTPS reverse proxy. Место размещения, домен/API origin, CPU/RAM, диски, firewall и режим внешнего LLM определяются совместно с ИТ до deployment.

## 8. Критерии готовности MVP

- выбранный пилотный корпус состоит только из явно approved источников;
- импорт повторяем и привязан к commit/hash;
- для каждого фрагмента сохраняются источник, раздел/страница и связи;
- retrieval проверен на русских обозначениях, латинице, протоколах и переформулировках;
- citations формируются backend и ведут к правильной странице/файлу;
- неподтверждённые факты не проходят evidence gate;
- система корректно уточняет неоднозначность и отказывает при отсутствии данных;
- внешний provider не получает неразрешённые chunks;
- качество проходит независимую приёмку по документу 06-acceptance-plan.md;
- API и минимальный UI проверены на целевой инфраструктуре;
- есть инструкция запуска, обновления, отзыва источника и восстановления.

## 9. Открытые решения

До начала пилота необходимо утвердить:
1. конкретный набор примерно из 10 источников и ответственного за проверку;
2. какие из них разрешены только локально, а какие могут передаваться внешней модели;
3. где размещается backend и каков доступный CPU/RAM/disk;
4. допустим ли внешний Qwen API и на каких условиях;
5. требуется ли OCR для выбранных PDF;
6. целевой язык первой версии (предлагается русский; английский — после проверки англоязычного корпуса);
7. условия и способ будущего подключения виджета к сайту.

До принятия этих решений нельзя считать пилотный корпус или production deployment готовыми.
