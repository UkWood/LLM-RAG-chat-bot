# План реализации технического консультанта Сатурна

Дата: 2026-11-08  
Версия: 0.1  
Принцип: сначала доказать качество на реальных разрешённых данных, затем строить пользовательский сервис.

## 1. Исходное состояние

В UkWood/LLM-RAG-chat-bot уже существует offline инженерное ядро: ingestion contracts, source registry, snapshot/policy contracts, BM25, локальные embeddings, Qdrant adapter, reranker, evidence gate и evaluation tooling.

Это позволяет не начинать RAG с нуля. Но текущие измерения сделаны преимущественно на synthetic corpus и не подтверждают качество на реальных материалах Сатурна.

Стабильный baseline — main commit bb16530e5b9a4943abae5c1b0f526cb218f46b2d. PR #12 с opt-in V3 находится в draft/unmerged; независимый blind quality gate не пройден (2/24 positive, 16/16 negative/ambiguity). Его нельзя автоматически считать принятым решением или включать по умолчанию.

## 2. Этапы

### Этап 0. Утверждение границ и ТЗ

**Цель:** согласовать назначение, ограничения, пилотный корпус, доступы и критерии качества.

Работы:
- рассмотреть пакет документов docs/site-specific/;
- утвердить принцип строгого read-only для сайта;
- назначить технического ответственного за проверку материалов;
- определить ориентировочный пилотный набор около 10 источников;
- решить, допускается ли cloud generation для конкретных материалов;
- согласовать критерии приёмки.

Результат: согласованная версия ТЗ, список открытых решений, ответственный за источники.

**Gate 0:** нельзя читать/загружать/индексировать реальные источники до явного решения об их допуске.

### Этап 1. Read-only аудит и адаптер источников сайта

**Цель:** сделать повторяемое извлечение данных сайта без изменений в репозитории сайта.

Работы:
1. Зафиксировать точный commit сайта и read-only способ доступа.
2. Реализовать/уточнить адаптер чтения Markdown/frontmatter из разрешённых коллекций.
3. Подключить нужные словари src/data/.
4. Сформировать export contract: entities, canonical facts, relations, source path, commit, hash, canonical URL.
5. Реализовать импорт каталога Support из documents/certificates опубликованных products/systems.
6. Сопоставить экспорт с поведением search-index.json и doc-index.json, не используя браузерные индексы как единственную KB.
7. Добавить contract fixtures и тесты на draft/category/software/relations/status.

Результат: read-only Knowledge Package в JSONL/JSON, с manifests и provenance.

**Gate 1:** повторный импорт одного commit/hash даёт идентичный пакет; ни одна операция не пишет в Saturn-Main-Site.

### Этап 2. Допуск и ingestion пилотных документов

**Цель:** создать небольшой проверенный корпус.

Работы:
1. Рассмотреть 8 существующих pending candidates и выбрать примерно 10 source objects для пилота.
2. Для каждой страницы проверить публикацию, содержимое, статус и hash.
3. Для каждого PDF отдельно подтвердить доступность, правильность редакции, физические страницы и SHA-256.
4. Получить реальное решение ответственного: visibility, approval state, allowed usage и cloud permission.
5. Загрузить только разрешённые PDF по точным allowlisted URL.
6. Проверить извлечение таблиц, единиц, списков, обозначений и страниц.
7. Пометить сканы/неполные документы; при необходимости провести отдельный OCR review.
8. Построить chunks с entity links, section/page anchors и версией parser.

Результат: первый real pilot snapshot; документы и страницы имеют проверяемые ссылки.

**Gate 2:** каждый индексируемый source имеет approved exact revision и hash; каждый PDF имеет проверенное содержимое. Неодобренные источники остаются недоступными.

### Этап 3. Site-aware retrieval и relation handling

**Цель:** адаптировать существующий поиск к реальным обозначениям и структуре сайта.

Работы:
- использовать словари интерфейсов, протоколов, синонимов, типов входов/выходов и названий характеристик;
- тестировать кириллицу/латиницу, дефисы, точки, цифровые индексы и сокращения;
- раздельно диагностировать site-content retrieval, Support catalog lookup и PDF-text retrieval;
- объединять результаты без потери source type;
- сохранять явные отношения изделий, систем, ПО, статей и решений;
- проверять полноту групп характеристик и не выдавать частичный список за полный;
- benchmark lexical, dense, hybrid и reranker на одном frozen real sample.

Результат: retrieval baseline с диагностикой и воспроизводимыми метриками.

**Gate 3:** правильный источник находится в Top-5 не менее чем для 90% положительных retrieval-вопросов пилотного набора; качество и ограничения задокументированы. Этот показатель — только retrieval gate, не приёмка ответов.

### Этап 4. Семантическое планирование, evidence gate и независимая оценка

**Цель:** обеспечить корректную интерпретацию естественных инженерных вопросов и полный ответ по evidence.

Работы:
1. Сформировать calibration dataset на реальных источниках.
2. Определить роли запроса: объект, параметр/отношение, документ, область применения, сравнение, ограничение, отрицание/оговорка.
3. Сохранять все части вопроса; не терять «нет», «только», Modbus/TCP/RTU, единицы, ограничения и действия.
4. Сопоставлять каждый требуемый факт с конкретным evidence.
5. Проверять полноту списков и таблиц; не выдавать неполные наборы.
6. Разделять отказ, уточнение и ответ.
7. Подготовить новую независимую blind evaluation set; автор и reviewer отделены от implementer.
8. После freeze выполнить единственный first blind run и сохранить отчёт. Не подстраивать код/порог под consumed blind set.

Результат: измеренная версия planner/evidence gate на real pilot corpus.

**Gate 4:** 24/24 положительных вопросов полностью корректны и 16/16 отрицательных/неоднозначных случаев получают корректный отказ или уточнение; 0 неподтверждённых технических утверждений; citations валидны. Если цель не достигнута — качество не принято, UI/cloud не должны маскировать проблему.

### Этап 5. LLM provider и API

**Цель:** подключить реальную генерацию только после достаточного качества retrieval/evidence.

Работы:
- проверить актуальный официальный OpenAI-compatible API Qwen/Alibaba Model Studio;
- получить отдельное решение на передачу конкретного PUBLIC корпуса внешнему provider;
- реализовать provider adapter с Fake и OpenAI-compatible implementations;
- настроить timeouts, limits, retries только для безопасных ошибок и provider diagnostics;
- backend формирует sources/citations и валидирует ответ;
- создать FastAPI endpoint и контрактные тесты;
- проверить отказ при недоступном provider и отсутствие leakage секретов.

Результат: API с реальным LLM provider, если egress разрешён; иначе полностью тестируемый offline provider path до решения.

**Gate 5:** неразрешённые источники не достигают cloud provider; citations и отказ проверяются backend; API выдерживает контрактные и security tests.

### Этап 6. Минимальный пользовательский интерфейс

**Цель:** предоставить простой способ задать вопрос и получить проверяемый ответ.

Работы:
- отдельный статический UI в AI-репозитории;
- поле ввода, отправка, ответ, источники;
- понятные состояния уточнения/отказа/ошибки;
- ссылки на страницу или оригинальный PDF, номер страницы;
- простая адаптация под desktop/mobile;
- ограничение частоты запросов на backend;
- не добавлять админку, аккаунты, CRM, аналитику или долгосрочную память.

Результат: standalone web prototype для ручной проверки.

**Gate 6:** пользователь видит ответ и реальные источники; никакой provider key или внутренний индекс не доступен из frontend.

### Этап 7. Закрытый технический пилот и эксплуатация

**Цель:** проверить систему на реальных вопросах с участием инженера.

Работы:
- развернуть backend на согласованном сервере;
- HTTPS reverse proxy, firewall, CORS и rate limits;
- Qdrant только localhost/private network;
- проверить CPU/RAM/latency/concurrency;
- настроить snapshot update, rollback, source revocation и backup;
- проверить логи, очистку и восстановление;
- собрать замечания инженеров, не меняя blind dataset задним числом.

Результат: ограниченный пилот, отчёт качества и эксплуатационная инструкция.

**Gate 7:** инженерный владелец подтверждает полезность и безопасность; все ограничения явно документированы.

### Этап 8. Отдельное решение о подключении к сайту

**Цель:** при необходимости сделать консультанта доступным посетителям публичного сайта.

Возможный вариант — независимый widget bundle/API origin, поставляемый из AI-репозитория. Способ подключения, место вставки и эксплуатационная схема согласуются отдельно. В рамках этого проекта нельзя самостоятельно менять Saturn-Main-Site.

**Gate 8:** интеграция выполняется только после отдельного явного разрешения владельца сайта. Отсутствие интеграции не блокирует standalone MVP и техническую приёмку.

## 3. Очерёдность и зависимости

~~~mermaid
flowchart TD
  A["0. Утвердить ТЗ и доступы"] --> B["1. Read-only adapter"]
  B --> C["2. Approved pilot corpus"]
  C --> D["3. Retrieval benchmark"]
  D --> E["4. Planner + evidence + blind evaluation"]
  E --> F["5. Provider + API"]
  F --> G["6. Minimal UI"]
  G --> H["7. Technical pilot"]
  H --> I["8. Optional site widget"]
~~~

Этапы 5–8 не должны начинаться в обход неуспешного quality gate этапа 4, кроме разработки технических заглушек/Fake provider и тестового UI, которые не заявляются как готовый продукт.

## 4. Definition of Done для каждого этапа

Каждый этап завершается:
- отдельным планом/ADR при изменении архитектуры;
- тестами, воспроизводимой командой и фактическим результатом;
- отчётом в docs/stages/;
- обновлением docs/PROJECT_STATUS.md и docs/HANDOFF.md;
- ссылкой на commit/PR и проверенными CI results;
- списком ограничений и следующим шагом.

Не объявлять этап завершённым по одному успешному запуску или зелёному CI. Кодовая корректность, retrieval quality, answer quality и production readiness — разные критерии.

## 5. Ближайшие задачи после утверждения документов

1. Согласовать точный список пилотных источников и владельца проверки.
2. Подтвердить доступность и права на 4 текущих PDF-кандидата либо заменить их.
3. Зафиксировать read-only способ получения snapshot сайта.
4. Проверить существующие ingestion contracts на соответствие полям Saturn-Main-Site.
5. Подготовить real-sample manifest и минимальные contract fixtures.
6. Только после допуска выполнить ingestion.
