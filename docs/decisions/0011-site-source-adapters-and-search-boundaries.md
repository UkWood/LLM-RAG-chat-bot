# ADR-0011: read-only адаптеры сайта и сохранение границ двух поисков

Дата: 2026-11-08  
Статус: принятые ограничения источников; детали реализации retrieval остаются предметом проверки на пилотном корпусе.

## Контекст

Сайт UkWood/Saturn-Main-Site — отдельный статический Astro-проект с Markdown/frontmatter, YAML-словарями, структурированными характеристиками и отношениями между изделиями, системами, статьями и решениями.

На сайте существуют две самостоятельные пользовательские поисковые функции:

1. /search/ — поиск по страницам и карточкам сайта через search-index.json и MiniSearch.
2. /service/search/ — поиск по каталогу документов поддержки через doc-index.json и отдельный metadata search.

Второй поиск находит файл по обозначению/названию изделия или системы и названию документа. Он не индексирует внутренний текст PDF. Первый поиск включает названия документов в карточках, но также не индексирует содержимое PDF.

Файлы поддержки физически размещены на старом файловом сервере и не входят в Git snapshot сайта.

## Решение

### Принятые границы

- Saturn-Main-Site является строго read-only источником. Запись в его репозиторий запрещена.
- Вся разработка, индексы и документация AI-консультанта находятся в UkWood/LLM-RAG-chat-bot.
- Существующие поисковые функции сайта сохраняются без изменений и не заменяются RAG.
- Доступ к Git snapshot должен быть read-only и привязан к конкретному commit/path/hash.
- Публичность страницы не означает автоматического допуска её версии к AI ingestion или cloud generation.
- Каждый внешний документ/PDF получает отдельный source record, hash и approval; допуск карточки не наследуется файлом.

### Предлагаемый способ использования источников

Создать три отдельных source adapters:
1. Site content adapter — структурированные записи и словари сайта.
2. Support catalog adapter — метаданные документов из documents/certificates опубликованных products/systems.
3. External document adapter — загрузка и извлечение текста только явно approved файлов по точным allowlisted URL.

RAG query orchestrator может объединять retrieval из этих каналов, но должен сохранять source type, provenance, revision, page/section и policy. Он строит собственные BM25/vector indexes и не зависит от внутреннего клиентского движка MiniSearch.

## Рассмотренные альтернативы

- **Изменять сайт ради RAG:** отклонено; нарушает read-only границу и создаёт ненужную зависимость двух проектов.
- **Использовать только search-index.json:** отклонено; это браузерная проекция контента с ограниченными текстовыми полями, а не полный корпус и не PDF index.
- **Использовать только doc-index.json:** отклонено; он содержит metadata каталога, но не текст файлов.
- **Сканировать старый файловый сервер целиком:** отклонено; неизвестны полнота, актуальность, права и назначение файлов. Источником discovery служат только явные ссылки из проверенного каталога.
- **Переиспользовать сайт MiniSearch как единственный backend:** отклонено; RAG нуждается в evidence, source policy, versioning, PDF pages и собственном retrieval/evaluation.
- **Пусть LLM сама выводит связи/совместимость:** отклонено; допустимы только явно заданные и provenance-linked отношения.

## Последствия

Положительные:
- сайт и его два пользовательских поиска не затрагиваются;
- консультант может отвечать и по карточкам, и по связям, и по тексту PDF;
- можно независимо развивать retrieval, embeddings, reranker и provider;
- у каждого ответа есть прослеживаемое происхождение.

Затраты/ограничения:
- нужно поддерживать адаптеры к схеме контента сайта;
- нужен отдельный процесс approvals и обновления source hashes;
- PDF ingestion требует контроля качества extraction;
- два или три retrieval channel усложняют diagnostics и evaluation;
- обновление сайта само по себе не означает автоматического обновления/допуска AI snapshot.

## Проверки для реализации

- read-only Git access;
- точное совпадение source commit/path/hash;
- draft filtering;
- различение system/category и product/software;
- корректное извлечение явных relations;
- metadata-only Support search не трактуется как PDF text;
- PDF fetch allowlist и hash;
- citations с canonical page URL либо original file URL + physical page;
- revoked/pending sources блокируются до retrieval и generation.

## Не решается этим ADR

Этот ADR не выбирает окончательную embedding model, reranker, LLM model, hosting provider, API domain или production deployment. Эти решения принимаются по результатам real-sample benchmark и согласования с ИТ.
