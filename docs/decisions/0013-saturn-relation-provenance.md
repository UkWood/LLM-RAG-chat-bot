# ADR-0013: provenance and semantic status of Saturn source relations

Дата: 2026-11-08  
Статус: **PROPOSED — owner approval required**  
Область: Site Content Adapter and canonical Knowledge Model  
Основание: site-specific v0.2, read-only audit of Saturn-Main-Site@084d759487bfab6e111549c9b5469711ac5fc13e.

## Context

The pinned site snapshot contains structured references in Markdown frontmatter, but their presence does not consistently indicate a manually reviewed engineering relation.

Audit of the actual source schema and migration scripts found:
- products.software, products.articles, products.solutions, systems.articles, systems.solutions, pages.products, pages.systems, news.products and articles.products/systems were generated by exact title-mention matching.
- products.related combines legacy good_id links and textual mentions.
- products.variant_of was generated by title-pattern heuristics.
- products.inputs/outputs were projected from specs, product designations and connector descriptions; the migration report records two source conflicts.
- products.systems mostly came from old catalog/group tables and can reference systems.kind=category.
- groups.system is a group-to-page/catalog mapping, not necessarily a technical relation.
- industries.yaml labels its mappings preliminary.
- The current Markdown records do not contain a reliable field-level reviewed_by or relation_origin marker.
- systems.summary is generated from the first suitable paragraph; applications comes from a hard-coded mapping; documents are extracted from Markdown links and their kind/version are heuristically assigned.
- pages.kind=solution and images, plus the groups on the resheniya page, are created by a migration script; groups.system is assigned by a mapping or slug match.

The existing check-content.mjs checks reference existence and controlled vocabulary, not engineering truth.

## Proposed decision

### 1. Separate source approval from semantic review

A SourceRevision may be approved for indexing/generation while a particular relation or derived field remains unreviewed.

These are independent controls:
- source-level approval_state and allowed_usage;
- field/relation-level review_state and semantic_origin.

An approved Markdown page does not automatically make every heuristic relation in its frontmatter an approved engineering assertion.

### 2. Store provenance for every relation

Every canonical Relation should include:
- relation_id;
- subject_entity_id;
- predicate;
- object_entity_id;
- source_id, revision_id;
- source_field_path;
- semantic_origin;
- derivation_method when derived;
- review_state;
- optional review_reference and reviewed_at.

Proposed semantic_origin values:
- source_declared — current field explicitly exists in source, but this alone does not imply human review;
- legacy_import — imported from legacy database/HTML relationship;
- heuristic_extraction — generated by text matching or pattern rules;
- derived_projection — reverse relation or normalized projection;
- navigation_structure — page grouping, menu, section or route association;
- taxonomy_mapping — industry/application/catalog classification.

Proposed review_state values:
- unreviewed;
- reviewed;
- approved_for_answer;
- rejected.

Do not invent numeric confidence scores. The provenance category and review state are more honest and auditable.

### 3. Preserve relation semantics; do not upgrade meaning

Examples:
- products.group → member_of_catalog_group;
- products.systems → catalog_or_system_association, then split by target kind;
- systems.kind=category → target type Category, never System;
- products.related → related_to, not compatible_with;
- heuristic products.software → software_mention_candidate, not verified compatible_with;
- articles/solutions references → mentioned_in or example_reference, not proof that a product is suitable for a given design;
- pages.groups.items → navigation_contains, not engineering relation;
- industries.yaml mappings → classified_under_preliminary_taxonomy.

A predicate such as compatible_with, implements, contains, required_for, supports_protocol or approved_for_use requires direct evidence or an explicit reviewed assertion. It must not be synthesized from co-occurrence or title mentions.

### 4. Preserve origin for derived facts

Also classify systems.applications as taxonomy_mapping unless a separate human-reviewed manifest exists. Classify generated systems.summary as summary_projection; inferred document kind/version as heuristic_extraction; generated page groups as navigation_structure. A current source field alone is not proof that a human has reviewed it.

For canonical facts, store:
- raw source field/value;
- normalized projection;
- semantic_origin;
- derivation_method;
- field_present;
- default_applied;
- review_state;
- source field path and revision.

Examples:
- inputs/outputs parsed from specs or title are derived projections;
- temperature_c, mass_kg, dimensions_mm, lifetime_years are canonical structured fields, but should retain raw specs values where available;
- systems.summary generated from first paragraph is a summary projection, not independent corroboration;
- default status=active must be distinguishable from an explicit status: active;
- default empty arrays are not evidence that a product has no capability or documentation.

### 5. Answer eligibility

Until owner review supplies a reviewed manifest:
- direct raw product/system facts from an approved exact source revision may be used with exact field provenance;
- raw Markdown passages may be used with heading/section provenance;
- heuristic relations may be used for navigation or candidate discovery only;
- navigation_structure and taxonomy_mapping are not technical answer evidence;
- related, software, articles, solutions, systems associations do not independently prove compatibility or system composition;
- conflicting projections fail closed;
- metadata-only Support Catalog entries may locate a document but cannot prove PDF contents.

A future approved_for_answer relation may be used only within its exact source revision and explicit semantic predicate.

### 6. Migration strategy

1. Do not rewrite Saturn-Main-Site.
2. In the AI repository, import raw records and retain field paths.
3. Attach provenance rules from audited migration scripts/reports.
4. Where the source cannot distinguish a hand-edited value from an old generated value, use legacy_frontmatter_origin_unknown and keep it unreviewed.
5. Create a separate review manifest for human-confirmed relations; never edit historical source fields to imply review.
6. Re-evaluate the mapping when a new site commit changes relevant fields.

## Consequences

Positive:
- no false upgrade from mention to compatibility;
- source and relation approvals remain separate;
- system/category distinction is preserved;
- contradictory projections remain visible;
- future human review can be applied without modifying the source site.

Costs:
- additional provenance fields and contracts;
- some relation-based answers are initially unavailable;
- human review may be required for important compatibility/composition claims;
- mapping must distinguish actual source fields from derived navigation/taxonomy.

## Not decided

This ADR does not choose:
- LLM/provider/model;
- embeddings/reranker/OCR;
- final database or index implementation;
- pilot document approvals;
- which individual relations a Saturn engineer will approve.

## Acceptance

This ADR is accepted only after the owner confirms:
1. semantic origin and review-state model;
2. relation eligibility rules;
3. treatment of the current heuristic software and related links;
4. whether the first pilot should answer from direct facts and approved document passages while excluding unreviewed heuristic relations.
