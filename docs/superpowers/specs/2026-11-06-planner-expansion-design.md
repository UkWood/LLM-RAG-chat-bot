## Goal and reason

Increase coverage of structured technical questions while preserving canonical quote/citation integrity, atomic current policy checks, explicit refusal and no cloud/provider downloads. The current QuestionPlan(entity_id,aspect) and full-question one-field grammar cannot represent multiple requirements, explicit source constraints or typed facts present in specs/tables/relationships. Adding isolated templates alone offers little evidence of generalization on already exposed questions.

The goal is a typed plan with requirement-complete validation and versioned fact projections, followed by a NEW blinded evaluation. This is bounded structured question understanding, not universal semantic entailment or natural engineering advice. No deployment, API/UI, real source approvals, new model weights or new dependencies in this first implementation.

## Approaches and recommendation

1. **Recommended:** compositional deterministic planner over a typed schema, with canonical fact projections and source constraints. Reuses current CPU models only for retrieval/reranking. Transparent why an answer is allowed/denied; covers structured requests beyond one-field regex. Cost: finite supported grammar and explicit projection schemas; unsupported language still refuses. It does not guarantee20/20 old questions or complete open-language understanding.
2. Semantic router using the existing local embedding/reranker models to propose typed requirements. Potentially broader paraphrase coverage, but rank score is not confidence; classification/abstention needs independent calibration and adversarial testing. A router can choose a true fact that answers the wrong question, which canonical quote validation cannot detect. Defer to a separately evaluated adapter after the typed contract exists.
3. Local generative planner with constrained JSON output. Broadest flexibility, but needs a new licensed model/runtime, resource measurements and semantic-plan validation. Defer; a free-form/cloud planner conflicts with current offline bounded scope and does not solve support by itself.

Recommendation1 is the implementer's proposal, not a production model or owner decision. No new source/cloud permission is implied. Owner can choose another approach before implementation.

## Query plan contract

Introduce immutable QueryPlanV2(requirements,question_sha256,planner_config_revision); each requirement is EvidenceNeed(entity_id,predicate,source_constraints). At most3 resolved entities/4 requirements, original question<=4000chars. Enums and field selectors only, never free text/URL/code from a planner. All needs resolve against one captured canonical snapshot/current eligible catalog. Unresolved entity/ambiguous selector → refusal/clarification before generation.

Predicates derive from parser schema/domain ontology: existing power/interfaces/protocols/temperature/status, exact named specifications, software feature/purpose, explicit system composition, approved manual reference and entity type. New predicates must be declared in versioned configuration before calibration and blind evaluation. No question IDs, expected answers or held_out-derived special rules in runtime.

source_constraints combines document_kind(any/product_card/manual) AND representation(any/structured_field/markdown_table/quoted_statement). Table structure is independent of document kind; qualifiers such as source kind constrain allowed evidence, not a suggestion the model may ignore. A product card is site_content in the products collection; manual is independently approved document_type=manual. A card cannot satisfy an explicitly manual-scoped need. A requested manual table requires BOTH constraints; PDF flat-text extraction currently cannot prove cell/header provenance, so such a need is unsupported until a separately verified projection exists. Never drop a constraint to return a related fact. Unknown requested scope or clause is unsupported, not silently dropped. Entity binding is exact designation by default, including complete suffix and Cyrillic/Latin distinctions. A designation one edit away still clarifies; no silent replacement. Optional type/relationship selectors (e.g. Software with an explicit configuration relation) must resolve to exactly one eligible entity, otherwise clarify; nearest-vector entity choice is forbidden.

Planner parses the complete query into clauses and consumes every requested predicate/entity/source constraint. Composition and comparison mean multiple independent supported facts, not inference of compatibility or causality. Explicit prohibition/unsupported qualifier/unparsed clause rejects the whole plan; no answer from one matched substring of a mixed/negated request. Documented grammar/aliases are versioned and frozen before evaluation; only calibration data may inform them. The existing v1 planner remains an explicit baseline, not an automatic fallback after v2 refuses.

## Canonical fact projection

FactProjection(entity_id,predicate,value,source_id,support_spans,parser_revision,unit,group_id,cardinality,complete) is an internal derived record, never model-authored evidence. Each CanonicalSpan(chunk_id,start,end,role) binds exact canonical text with role subject/value/header/relation. Multiple spans are required when entity row, value cell and unit/header are separate; no single approximate substring substitutes for row/column binding. Spans refer to the exact canonical parsed chunk; original source hash/page/heading remain authoritative. Projections are rebuilt deterministically from the captured snapshot and a versioned projection schema, validated against its canonical bytes/text. No raw corpus/projection dumps committed to Git.

No canonical parser/snapshot format change is included in this first implementation. Current Relationship/entity_type metadata without quotation chunks must not masquerade as span-supported engineering facts. Relationship metadata can resolve selectors or hint retrieval only; a relationship/purpose/composition claim still requires an independently quotable declared statement. EntityTypeReference and DocumentReference are separate backend metadata result variants validated directly against canonical Document/registry plus an eligible same-source title/page anchor; they are not FactProjection quotations or model-generated engineering claims. Reference display is a literal typed value/approved title/URL, never an inferred compatibility/causal statement. All-reference requests bypass Fake provider after the same gate/policy checks; mixed requests generate quotes only, then append independently validated references. Result schema v2 is explicit/opt-in; v1 remains unchanged.

Initially project:

- Existing typed site fields and named specs with their explicit labels/units. Counts must remain counts; voltage/current/temperature units cannot be guessed or exchanged.
- Markdown tables with an explicit recognized header, explicit entity in its row and unambiguous column/units. Preserve source/row/column span provenance; no inference from mere numeric co-occurrence or absent cells.
- Explicit canonical relationships (software/system/component) plus narrowly declared statement grammar for a feature/purpose/composition. Mere co-occurrence of products does not establish a relationship or compatibility. Unparsed narrative remains unprojected; do not treat arbitrary body text as a universal fact.
- DocumentReference uses independently approved document metadata and a real canonical physical-page anchor. It is distinct from an extractive engineering claim: backend may render registry title/URL/hash, not have FakeLLM invent them. Pending links are never references. If anchor expansion is needed, allow one canonical same-document lookup from an already retrieved approved manual, charge it to the same top5/8000char evidence budget, and record it separately from ranked evidence. This cannot add a different source/entity or answer arbitrary unranked facts.

A table row/header or named spec may create several projections anchored to one chunk; it counts as ONE source of evidence, not independent corroboration. Value normalization only for explicitly equivalent forms/units; no silent conversion. Malformed/missing/ambiguous typed value quarantines the relevant requirement. Cardinality/completeness is part of the versioned predicate schema: power/temperature/status/named-spec-by-label/purpose/type/reference are scalar per entity and applicable source constraints; interfaces/protocols/features/composition are set-valued. Distinct members within ONE complete source group are legitimate, not conflicting scalars. Complete groups for the same entity/predicate/constraints must agree as sets; partial enumerations cannot establish completeness. Parsed partial subsets of an agreed complete group do not add proof; an incompatible parsed partial fact conflicts, and malformed/unknown completeness refuses. Explicit open-list markers such as examples/"and others" do not create a complete group. No union of partial sources is promoted to a complete answer. Different complete current eligible scalar values or complete source sets conflict; no highest-score/latest-version guessing. Distinct aspects must not be treated as conflicting values.

## Evidence gate and generation

Reuse captured IndexSet, unchanged hybrid/RRF/reranker, atomic multi-scope local_index+local_generate check, and current revocation checks. Both plan and projection schema revisions are pinned in trace/report. Every requirement must have supporting selected evidence and explicit provenance. If ANY need is missing/ambiguous/conflicting/budget-exceeding, no provider call for the entire request. Never emit a partial comparison as a complete answer.

Keep final evidence<=5 canonical chunks/8000chars. Record per-need coverage and anchor expansions in diagnostics without raw question/context logging. Projections establish field binding; provider still receives only approved canonical quotation evidence. Generated numeric values/units must not come from normalized projection strings or model calculations: emit verbatim quotes (or typed backend document references), never paraphrased or synthesized facts under this stage's support claim.

Provider only offline/test FakeLLMProvider. Validate complete unique exact quote claims per requirement and separately backend-built document/type references; no model-provided URLs/pages/entity IDs. Current policy checked before/after provider and before result with one atomic multi-scope eligibility read at each boundary. Metadata/citation validation is not arbitrary Python-provider sandboxing or universal semantic correctness. Existing M1 and v1 evaluation remain available, no silent production/default switch.

## Calibration and fresh evaluation protocol

The old30cases and reports are immutable LEGACY REGRESSION. Their historical calibration/held_out labels remain, but the exposed held_out is no longer independent evidence for a redesigned planner. Only old calibration cases may inform tuning. Improvements on old held_out may be reported as regression outcomes, never as new blind generalization. No target-case patches or rewritten gold labels/metrics.

Before implementation/tuning, an independent author with fresh context creates a new synthetic dataset from approved canonical KB and this CAPABILITY schema only. They must NOT read old datasets/reports or candidate implementation/grammar. Proposed set:40 questions:24 supported positives (8 single typed-field/named-spec,4 multi-need,4 source-constrained,4 document references,4 quotable relationship/entity-type queries),8 mandatory refusals (unsupported fact/compatibility/unknown entity/injection),8 ambiguity/unsupported-mixed/negated cases with explicit expected outcomes. A fully supported multi-need composition belongs among positives, not automatic refusals. If a capability has no verifiable canonical projection/reference in this KB, authoring must report the gap BEFORE freeze rather than invent support or change allocation after seeing results. All text/evidence labels validated against canonical hashes/pages/fields/relationships; require independent label review. This is a proposed sampling design, not an expert engineering benchmark.

Commit the dataset and SHA256 manifest, keep text/labels hidden from implementer until freeze. No new source documents needed. Freeze code/config/calibration thresholds/aliases/projection schema at an exact commit and declare the blind evaluation START before reading/using blind contents. First run only once; save ALL cases/errors with stable code/model/snapshot/dataset/config identities. Dataset author/label reviewer may inspect labels before freeze; implementer may inspect only manifest/counts/hash and validation result. After first result, any further tuning consumes this set as regression and requires another fresh blind set before a new generalization claim.

Use existing pinned E5+reranker and offline Fake provider; no test graph substitutes for model quality. Compare v1 and v2 on the SAME new set with unchanged retrieval settings. Report status accuracy, supported-positive answer rate, false refusal/clarification, expected-fact/requirement coverage, unsupported claim/citation/plan-binding violations, exact quote support, mandatory refusal/ambiguity outcomes and infrastructure errors with proper denominators. The new rubric normalizes v1 canonical citations and v2 typed references into the SAME reference-correctness checks for reference-only needs, so output-format change cannot manufacture a win. Do not change v1 legacy metrics to favor document lookup: document-reference correctness and quoted-fact coverage are separate explicit measurements; preserve old legacy expected-evidence score unchanged.

Acceptance fixed BEFORE seeing blind questions/results: no v1 positive-answer regression on legacy calibration; strict code/policy/provenance tests all pass; on the NEW set all24/24 supported positives must be fully correct and all16/16 mandatory refusal/ambiguity outcomes correct, with no unsupported factual claims, invalid citations/source-policy leakage or partial-need answers. Improvements below this goal are measured progress, not a passed quality gate. This does not lower the accepted full-set criterion and does not declare complete production/prototype acceptance. No default enablement on any unsafe answer or unmet experimental quality target; existing v1 path remains available. These are proposed design criteria to approve before implementation/evaluation.
