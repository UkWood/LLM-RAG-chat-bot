# Обычный RAG с подтверждённым частичным ответом

Дата: 2026-11-07. Статус: **принят владельцем для реализации обсуждённого подхода**.

Владелец выбрал направление «обычный RAG с проверкой подтверждений», включая ответ своими словами, частичные ответы и обращение к поддержке при пробелах. После уточнения автоматических обновлений, расписания и готовой API-модели владелец прямо попросил применить рассуждения к проекту. Это разрешение реализации обсуждённого направления; недостающие endpoint/key остаются входами для реальных вызовов. Основание: [исходное ТЗ](../../requirements/original-brief.ru.md), [критерии прототипа](../../acceptance/prototype-v1.md). Изменение ранее принятого поведения all-needs описано явно ниже.

## Зачем меняем направление

Нужен консультант для посетителя: вопрос обычным языком → сведения из разрешённых страниц и документов → понятный ответ со ссылками. Нельзя дополнять материалы общими знаниями модели, придумывать параметры, совместимость, выводы или ссылки.

Существующие ingestion, snapshots, PUBLIC policy, BM25/E5 hybrid retrieval и локальный reranker сохраняют ценность. Формальный перевод каждого вопроса в заранее известные predicates перед поиском стал препятствием. В независимом V3 эксперименте полноценно отвечены2/24 положительных вопроса против4/24 у V2; открытая calibration35/36 не перенеслась на новые формулировки. Все22 пропущенных положительных вопроса остановились на разборе/маршрутизации до retrieval. [Неизменный отчёт V3](https://github.com/UkWood/LLM-RAG-chat-bot/blob/2ea295197fffebde354a1e843bac464503dd5724/evaluation/reports/2026-11-07-planner-v3-first-blind.json), [draft PR12](https://github.com/UkWood/LLM-RAG-chat-bot/pull/12). Его dataset/START/результат остаются историческими: новая архитектура не настраивается на потреблённом blind-наборе.

## Что выбрал владелец

Рассмотрены два подхода:

| Подход | Польза | Ограничение |
| --- | --- | --- |
| **Обычный RAG + проверка подтверждений — выбран** | LLM понимает формулировку и объединяет сведения в связный ответ; подтверждённая часть полезна даже при пробелах | Смысловую корректность нужно измерять; проверяющая модель тоже может ошибаться |
| Ответ преимущественно дословными выдержками | Прямое происхождение текста проще проверять | Пользователю приходится самому собирать ответ из выдержек; хуже для сравнений и нескольких документов |

Формальный planner не является обязательным посредником между вопросом и поиском. Предыдущие версии не удаляются и не переписываются ради нового результата.

## Пользовательское поведение

1. Дать конкретный ответ на подтверждённые части вопроса со ссылками на источники.
2. Обозначить каждую существенную неподтверждённую часть конкретным вопросом и направить в поддержку компании.
3. Не превращать отсутствие сведений в утверждение об отсутствии функции или возможности.
4. Если ничего не подтверждено, не добавлять технический ответ из памяти модели; показать вопрос к поддержке.
5. Не выбирать произвольно между противоречащими документами. Независимые подтверждённые сведения можно оставить; конфликтующую часть обозначить вопросом к поддержке.

Пример формы, только при наличии соответствующего подтверждения:

> Контроллер поддерживает RS-485 — [источник].
> Поддерживает ли он также BACnet? В доступных материалах это не указано. Для уточнения свяжитесь с поддержкой компании.

При полном пробеле:

> Можно ли использовать этот контроллер в указанных условиях? В доступных материалах я не нашёл подтверждения. Для уточнения свяжитесь с поддержкой компании.

Поддержка — действие пользователя. Бот не отправляет сообщения, не создаёт заявку и не утверждает, что компания получила вопрос. Текст «Для уточнения свяжитесь с поддержкой компании» формирует backend один раз после списка вопросов. Реальную ссылку/телефон/email берём только из проверенной настройки; пока её нет, остаётся текст без выдуманного адреса. Конкретный контакт задаётся перед публикацией UI, он не блокирует CLI-диагностику.

Неоднозначное обозначение изделия можно уточнить у самого пользователя, не выдумывая модель. Ошибка поиска/provider/проверки имеет status=error, а не «в документах этого нет»; сообщение сообщает о невозможности проверки и при необходимости предлагает связаться с поддержкой. Отсутствие результатов поиска означает отсутствие подтверждения в доступных материалах, а не доказанное отсутствие информации во всём архиве.

## Изменяющийся сайт: содержание важнее классификаторов

Дополнение владельца: опубликованные изменения должны попадать в KB автоматически. Сайт находится в разработке; категории и классификаторы характеристик будут меняться и упрощаться. Актуальными источниками являются содержательные тексты страниц и PDF, на которые ссылается сайт. Система не требует стабилизации таксономии для начала полезной работы.

Основой retrieval служат текст страницы, технические таблицы как содержание и текст/таблицы PDF с provenance. Названия категорий, schema keys и группировка характеристик могут быть вспомогательными metadata, но не обязательной схемой фактов/intent, источником технического вывода или условием допуска вопроса к поиску. Переименование категории/поля при неизменном содержании не должно ломать поиск и ответы. При смене URL обновляются locator/citations; смена таксономии сама по себе не требует замены LLM или embedding-модели. Опубликованный текст извлекается независимо от нестабильной структуры исходного frontmatter; меню/навигация не подменяют техническое содержание.

Scope автоматизации: опубликованные страницы согласованного сайта и публичные PDF, на которые эти страницы непосредственно ссылаются. Разрабатываемые ветки/PR и весь GitHub repository автоматически в KB не включаются. Внешний PDF может обнаруживаться по прямой ссылке доверенной страницы; скачивание всё равно проходит проверки публичного URL, redirect/DNS/IP, типа и размера файла. Это не произвольный обход внешних сайтов и не разрешение пользовательских URL. Прочие форматы архивов требуют явно определённого ingestion support; их наличие не означает успешную индексацию.

Новая версия конкретного разрешённого материала допускается по принятой владельцем автоматической policy, без ручного согласования каждого hash. Для аудита сохраняются policy revision, URL/ссылка-источник, наблюдавшаяся публикация, время проверки и exact content hash каждой версии. Это явное предложение заменить ручной per-version workflow в пределах согласованного scope; текущий runtime registry в этом docs-only изменении не меняется. Новые типы/границы источников, cloud egress и INTERNAL не разрешаются автоматически. Принимается публичный опубликованный контент, а не непроверенный development snapshot.

Обновление выполняет отдельный процесс консультанта, без изменения Saturn-Main-Site. Он сверяет страницы, ссылки и bytes/hash PDF, обнаруживает добавления/редакции/удаления, повторно извлекает изменённое содержание и строит согласованный snapshot BM25+dense/chunks. Неизменившиеся данные переиспользуются. Готовая проверенная версия включается атомарно; один запрос не смешивает разные snapshots.

После подтверждённого удаления/отзыва или изменения устаревшая версия блокируется текущей policy до завершения переиндексации, включая запросы в работе. До/после LLM и перед ответом перепроверяются использованные версии; оставшиеся независимые утверждения можно дать частично, заблокированная часть становится вопросом к поддержке. Если у PDF исчезла последняя доверенная ссылка, по умолчанию он выходит из scope, кроме отдельно зарегистрированного независимого KB-источника. Сетевой сбой не приравнивается к удалению: сохраняются last-success и состояние актуальности, а не притворный успешный refresh.

Кеш, если появится, привязывается к snapshot/policy/source revisions и инвалидируется при изменении использованных источников. Предыдущие ответы в истории не являются evidence для следующего вопроса; факты заново проверяются по текущей базе. У ответа сохраняются использованные версии и дата актуальности. Уже выданный ответ нельзя задним числом сделать актуальным; интерфейс может отметить обновление его источника. Исторические версии не используются по умолчанию для новых ответов.

Владелец установил расписание: автоматический запуск обновления один раз в сутки и принудительный запуск администратором в любой момент. Время суток и timezone задаются конфигурацией deployment, не зашиваются в бизнес-логику. Ручной запуск доступен только авторизованному администратору консультанта (для начального CLI — операторская команда); он не меняет сайт и не обходится через пользовательский чат. Одновременные запуски не публикуют конкурирующие snapshots: updater сериализует/объединяет повторный trigger и показывает running/pending/completed/failed, время последнего успеха и ошибки. Обновляется только согласованный scope; принудительный запуск не расширяет permissions. При ошибке новая неполная база не публикуется, фиксируется сбой и уведомляется администратор. Между плановыми проверками действует последняя успешно опубликованная версия; важное изменение администратор может подхватить вручную. Возможное окно обнаружения — до следующего успешного запуска плюс обработка, а не мгновенная синхронизация. Предельный возраст базы при длительных сбоях задаётся отдельной явной operational policy; старые данные нельзя выдавать за только что проверенные. При превышении согласованной границы нельзя молча выдавать старые факты как проверенные актуальные. Перед приёмкой нужны сценарии edit/add/delete, замена PDF по прежнему URL, переименование категории при том же тексте, удаление ссылки, сбой загрузки/индексации, переключение snapshot и отзыв во время ответа. Это проверки актуальности источников, отдельно от качества языка LLM.

## Простой основной путь

1. Проверить допустимость запроса, размер и текущую source policy. Перед облачной отправкой отдельно проверить privacy/egress. Не требовать известного intent, схемы фактов или ограниченного алфавита; обычные кавычки и естественные уточнения не блокируют поиск. Исходный вопрос сохраняется без потери обозначений/отрицаний/условий.
2. Искать по исходному вопросу в согласованном snapshot: существующий hybrid BM25+dense → существующий локальный reranker → ограниченный контекст. На первом шаге нет planner, model-written query, agent tools или серии уточняющих поисков.
3. Передать разрешённые фрагменты вместе с полным вопросом сменной LLM. Документы — данные, инструкции внутри них не исполняются. Модель формирует короткие утверждения с указателями на подтверждающие выдержки и предлагает вопросы о пробелах.
4. Проверить утверждения и покрытие исходного вопроса; оставить только прошедшие проверку. Неудачное утверждение превращается в пробел, а не в повод удалить остальные подтверждённые части.
5. Backend собирает окончательный текст, ссылки и вопросы к поддержке. Перепроверяет разрешения до передачи контекста, после генерации и перед публикацией; отозванные сведения не выводятся.

Сохраняются существующие поисковые ограничения: channel limit40, dedup pool30, rerank до30 passage pairs, контекст до5целых chunks/8000символов. Это **выбор автора дизайна для первого измерения**, а не новый согласованный SLA. Полный вопрос должен вмещаться в provider request; нельзя молча отрезать его условия. Ограничение модели при reranking является ограничением ранжирования, не доказательством правильности ответа. Пересмотр context budget возможен позже по отдельному измерению recall, не ради подгонки blind.

Не делаем сначала большой универсальный planner, граф знаний, новую БД или новый framework. CLI достаточно для первого доказательства полезности. API/UI/деплой и интеграция в сайт остаются последующими этапами.

## Что именно означает проверка подтверждений

Внутренний draft содержит отдельные короткие утверждения, для каждого — IDs переданных chunks и точные выдержки/позиции, а также список вопросов о непокрытых частях. Здесь нет enum технических predicates или обязательного формального плана пользовательского вопроса. Точную структуру JSON и классы выбирает implementer, сохраняя разделение draft и verified result.

**Детерминированная часть:** IDs присутствуют в переданном контексте; выдержки точно совпадают с каноническим текстом; metadata/URL/страницы берутся backend; лимиты и разрешения соблюдены. Строго проверяются сохранность названий, чисел, единиц, отрицаний и условий в сопоставлении с подтверждением. Эти проверки не заменяют понимание смысла и не получают права блокировать произвольные формулировки до поиска.

**Смысловая часть:** отдельный bounded verification pass получает исходный вопрос, draft и подтверждающие выдержки. Для каждого утверждения оценивает, следует ли весь его смысл из выдержек, включая нужное изделие, условия, полноту перечней и отношения между объектами. Проверяет и пробелы: нельзя пропустить существенную часть вопроса или подменить её похожим свойством. Статусы supported/unsupported/uncertain; последние два не публикуются как факты. Новые предположения о совместимости и инженерные выводы без прямого основания запрещены. Вопрос к поддержке тоже не должен содержать выдуманные предпосылки.

На первый вариант — один generation pass и один verification pass, без цикла самопереписывания/агентов. Проверка может использовать того же настроенного provider, но её ошибки коррелируют с генератором. Это **проверяемая гипотеза, а не доказательство отсутствия галлюцинаций**. Решение о допустимости натуральной генерации принимается по чтению реальных ответов и evidence человеком на проверочных вопросах. Если проверка не отличает неподтверждённые утверждения, её нельзя объявлять готовой на основании корректного JSON или цитат; следующий шаг пересматривается по измерению, а не очередной таблицей intents.

Нельзя гарантировать абсолютную безошибочность свободного пересказа одной инструкцией/вторым LLM-вызовом. Пользовательское требование остаётся строгим: публиковать только подтверждённое. Неуверенность уменьшает фактическую часть ответа и добавляет вопрос к поддержке; ошибки checker/provider дают error. Нулевое число обнаруженных ошибок на небольшом наборе не становится универсальной гарантией.

## Переиспользование и границы изменений

Новое поведение требует отдельного пути orchestration/response, потому что текущий Claim/FakeLLMProvider и exact-quote validators предполагают дословные quotes, а V2 требует все needs. Их нельзя незаметно ослабить и продолжить ссылаться на старые тесты. Существующие V1/V2 contracts и benchmarks сохраняются; новый путь принимает подтверждённый частичный ответ. После утверждения дизайна отдельно обновляются применимые критерии приёмки/ADR; старые результаты не переоцениваются задним числом.

Собственная LLM, обучение с нуля, fine-tuning и дистилляция для проекта не планируются. Используется готовая обученная модель через API; исходный предпочтительный вариант — семейство Qwen, а конкретные model/endpoint/region проверяются и конфигурируются перед интеграцией. Уже готовая дистиллированная модель тоже допустима как provider, если её API/качество проверены; дистилляция не является нашей задачей. Впоследствии готовую модель можно разместить локально за совместимым API, сохранив retrieval и KB, с отдельной проверкой качества provider. Суточный updater обновляет документы/chunks/поисковые embeddings, не веса LLM. Во время ответа готовая LLM получает вопрос и только отобранный разрешённый контекст.

Provider остаётся OpenAI-compatible и сменным; endpoint/model/key задаются backend-конфигурацией, не бизнес-логикой. Existing Fake остаётся для unit/contract tests, не для доказательства качества натурального ответа. HTTP adapter проверяется mock endpoint без cloud. Для реального диагностического прогона обязательно нужен фактически доступный и разрешённый LLM runtime. Выбор конкретного cloud/local endpoint/model — отдельный входной параметр перед этим прогоном; данный дизайн не выбирает и не загружает новую модель, не разрешает cloud. Без runtime natural-generation quality = NOT_RUN, а не ещё один «успешный» Fake benchmark.

Saturn-Main-Site строго read-only. Версии опубликованных страниц и непосредственно связанных публичных PDF допускаются по согласованной автоматической policy выше; arbitrary ZIP/прочие форматы и неизвестные источники автоматически не разрешаются. Никаких пользовательских URL/самостоятельного обхода архивов во время ответа. PUBLIC/index/generate/egress ограничения остаются жёсткими. Нет нового допуска реальных sources, cloud, INTERNAL, зависимостей или automatic fallback.

## Первый диагностический шаг вместо новой большой реализации

После утверждения документа строится минимальный CLI-путь и HTTP/mock contract. Перед расширением архитектуры провести небольшое диагностическое измерение с настоящей разрешённой LLM. При недоступном runtime остановить этот этап со статусом NOT_RUN и конкретным отсутствующим условием; не строить очередной substitute planner.

Выбор автора для первоначального масштаба:15новых открытых вопросов (5полных ответов,4частичных,3без сведений,2неоднозначных,1конфликт). Они отражают сценарии исходного ТЗ и указывают ожидаемые факты/пробелы и точные источники. Человек проверяет пригодность вопросов до использования. Сначала допускается отдельный synthetic профиль на существующей fixture KB; результат честно называется synthetic. Для выводов о сайте нужен отдельно допущенный реальный sample и соответствующие вопросы, а не перенос synthetic результата. До такого прогона manifest явно фиксирует проиндексированные документы, поддержанные форматы и ошибки извлечения; неподдержанный файл архива нельзя выдавать за успешно прочитанный. Старые потреблённые blind sets не входят в tuning.

На одних и тех же диагностических вопросах отдельно измеряются:

- Retrieval без planner: нашлись ли нужные фрагменты, сохранились ли они после reranking/context cut. Для частичных случаев gold описывает только действительно существующие сведения.
- Generator+checker с заранее правильным контекстом: умеет ли LLM дать подтверждённый ответ/часть, указать пробелы и не изобрести факты даже при идеальном поиске.
- Полный путь: что теряется при соединении компонентов; правильны ли вопросы к поддержке.

Отчёт различает полные/частичные корректные ответы, ложные отказы, неподтверждённые утверждения, верность citations, пропущенные части и infrastructure errors. Повторный validator той же схемы и self-score генератора не считаются независимым quality grader. Первую смысловую оценку делает человек по исходному вопросу и evidence; backend делает проверяемую часть. Fixture/Fake тесты и измерение LLM публикуются раздельно.

Это открытая диагностика, не приёмочный blind и не обещание production. Критерий перехода к следующему небольшому этапу: все три измерения реально выполнены, ошибки локализованы, человек проверил ответы, наблюдаемые неподтверждённые утверждения не замаскированы средней метрикой. Если unsupported claims есть, способ проверки не принимается; разобрать этот механизм до расширения. Следующие численные coverage targets и отдельный свежий независимый набор согласуются до финальной приёмки по пригодным бизнес-сценариям; исторические24/24+16/16не объявляются выполненными и не понижаются задним числом.

Unit tests закрепляют конкретные воспроизведённые ошибки и policy/provider/citation boundaries. Не писать отдельные правила под каждую формулировку вопроса. Повторять дорогой LLM-прогон только при изменениях проверяемого компонента или unresolved failure; docs-only изменение не повод повторять model benchmark. Существующий GitHub CI сохраняется. После диагностической готовности — один замороженный независимый прогон, не новый blind после каждой правки.

## Что сознательно остаётся следующему этапу

Implementer выбирает названия модулей, внутренние JSON-классы, безопасные timeouts/output bounds и тестовые doubles. Начальный scope автоматической policy фиксируется по выбранному сайту и прямым PDF-ссылкам; реальный диагностический sample выбирается внутри него с manifest версий, без повторного ручного одобрения каждой публикации. Владелец отдельно предоставляет/подтверждает разрешённый runtime/egress и контакт поддержки перед соответствующими действиями. Это не блокирует написание плана с явными зависимостями; отсутствие входов блокирует только зависимые реальные вызовы/публикацию. Новые dependencies выбираются только при необходимости с отдельным обоснованием.

Реализация первого CLI/диагностического этапа разрешена. Реальные API-вызовы требуют готового разрешённого runtime и публичного контекста; merge/deploy автоматически не выполняются.
