# Первый полноценный RAG-прототип: согласованные критерии приёмки

Дата согласования: 2026-11-05. Статус: **accepted — критерии, не результат приёмки**.

Основание: владелец предоставил [исходный документ](../requirements/prototype-acceptance-original.ru.md), обсудил расхождения с текущей работой и ответил «Согласую» на предложение применять его как дополнение к roadmap с двумя профилями. [ADR-0004](../decisions/0004-prototype-acceptance.md) фиксирует границы согласования.

Документ дополняет [roadmap](../superpowers/plans/2026-11-03-ai-consultant-roadmap.md). Термин «первый прототип» здесь шире выполненного M1: включает проверенный ingestion, hybrid retrieval, reranking и grounded pipeline (этапы 2–5). Проверка OpenAI-compatible HTTP adapter относится к отдельной проверке протокола этапа 6. Завершение M1 или green unit tests не означает приёмку этого прототипа. UI/API и cloud не становятся обязательными для offline-профиля.

## 1. Цель и границы

Доказать, что небольшая контролируемая KB позволяет найти правильные источники, выдать только подтверждённые факты и корректно отказать без evidence. Приоритет: правильный источник → правильный отказ → grounded answer → воспроизводимая проверка → сменный provider.

Достаточно CLI. Финальный frontend, интеграция с Astro, индексация всего сайта, INTERNAL KB, авторизация, сложная память диалога, production local LLM, GPU, автоматический cloud fallback и fine-tuning не входят в приёмку. Saturn-Main-Site строго read-only.

## 2. Два независимых профиля

| Профиль | Данные и выполнение | Что доказывает |
|---|---|---|
| A — synthetic offline | Около 10 authored вымышленных документов разных типов, включая 1–2 содержательных учебных PDF и таблицы. Отдельный test-only manifest, FakeLLMProvider; CPU, без сети во время тестов, ключей и многогигабайтной LLM | Корректность pipeline и измеренное качество поиска на зафиксированном синтетическом наборе |
| B — допущенный реальный sample | Около 10 проверенных документов сайта/руководств с exact revision approvals и provenance. Локальные embeddings/reranking, проверка фактов инженером; загрузка/парсинг только по действующей policy | Качество на реальной документации в пределах проверенного sample; не production readiness |

Количество документов — ориентир разнообразия; фактический состав и версии записываются в manifest. Один и тот же документ, нарезанный на chunks, не считается несколькими независимыми документами. Структура вопросов и отчётов общая, но наборы данных разделены. Синтетические результаты не переносятся на реальную продукцию и не считаются результатами профиля B. Реальные обозначения нельзя снабжать вымышленными характеристиками.

Профиль B не требует облачного вызова: поиск, provenance и факты можно проверять локально. Реальная свободная генерация требует отдельной проверки поддержки утверждений; Fake доказывает только свой сценарий. Cloud smoke допускается лишь отдельным шагом после требований раздела 3.

## 3. Допуск и конфиденциальность

Сохраняется [PUBLIC policy](../public-source-policy.md): PUBLIC — необходимое, но недостаточное условие. Требуются approved exact hash/revision, publication verification, provenance и соответствующий scope. UNKNOWN/pending/revoked запрещены. Карточка не разрешает автоматически её PDF. Синтетические fixture approvals не являются решениями владельца о реальных источниках.

Перед облачным вызовом дополнительно нужны cloud_allowed + cloud_generate, privacy-проверка вопроса/истории, разрешённый endpoint и условия провайдера. Одобрение этих критериев **не допускает реальные источники, не разрешает cloud и не принимает всю proposed production architecture**. API keys остаются на backend; .env не коммитится, .env.example появляется с provider configuration без секретов. Qdrant не публикуется в Internet.

## 4. Ingestion и metadata

- Каждый разрешённый документ импортируется воспроизводимо; ошибки, неполные результаты, hash/commit drift и плохое извлечение не превращаются в молчаливый успех.
- Chunks сохраняют связь с document/source, исходный hash, heading/field provenance, технические значения/единицы и access-policy metadata. Для будущего индекса visibility и policy revision должны сохраняться и проверяться; одной потери связи с реестром допускать нельзя.
- Chunking учитывает разделы, абзацы, списки и таблицы. Заголовки/единицы таблицы сохраняются вместе с значениями.
- Для PDF-источника ответа требуется подтверждённая физическая страница. Если извлечение её не обеспечивает или непригодно для фактов, документ/фрагмент отклоняется, страница не угадывается. OCR/сложные таблицы требуют отдельной проверки качества.
- INTERNAL и неразрешённые источники не достигают provider. Отзыв проверяется до генерации и перед выдачей.

## 5. Retrieval, reranking и evaluation

Нужны local semantic/vector + lexical/BM25 поиск, видимое объединение кандидатов и сменный reranker. Результаты каждого шага доступны в developer diagnostic mode. Интерфейс reranker позволяет проверять pipeline с test adapter, но такой тест не доказывает качество реального reranking. Аналогично deterministic embeddings не подтверждают semantic search.

Подготовить около 30 постоянных контрольных вопросов с распределением из исходного документа: характеристики 5, точное обозначение 4, переформулировки 4, несколько фрагментов 3, документ/руководство 3, опечатки 2, без ответа 3, несуществующее изделие 2, injection 2, вне области 2.

Хранить id/question/expected_sources/expected_facts/must_answer/must_refuse/tags; при неоднозначном обозначении указывать expected_status=clarification. Поля ожиданий должны быть непротиворечивы. Опечатка не разрешает молча подменить изделие; допустимый исход каждого случая размечается заранее.

Для зафиксированного малого приёмочного набора профиля A правильный источник должен попасть в Top-5 для **каждого must_answer**: source-hit@5 = 100% на этом наборе. Дополнительно измерять chunk relevance и покрытие всех expected sources для multi-doc, а не считать один случайный hit доказательством полного ответа. Для профиля B пороги качества определяются по baseline и согласуются до окончательной приёмки; слово «обычно» не считается численным критерием.

Отчёт содержит corpus/dataset/config/model/provider revisions, per-question outcome, источники/факты, отказы и ошибки, Top-5 показатели, citation validity, unsupported claims и false refusals. Нужны отдельные calibration и held-out данные для настройки порогов; 30 вопросов — ранний baseline, а не доказательство универсальной надёжности. Поиск можно оценить с FakeLLMProvider, качество естественной генерации — только с фактически проверяемым provider.

## 6. Ответы и отрицательные сценарии

Backend формирует source IDs, названия, URLs и страницы из разрешённых metadata; LLM их не придумывает. Каждое техническое утверждение должно иметь поддержку текущего evidence. Валидный source ID сам по себе не доказывает истинность утверждения.

Нет evidence → refusal без использования общих знаний модели. Правдоподобное отсутствующее изделие → refusal. Неоднозначность → clarification. Конфликт evidence не разрешается произвольным выбором факта. Ошибка инфраструктуры имеет status=error и не маскируется под отсутствие данных.

Обязательны user/document injection, INTERNAL isolation, выдуманные claims/metadata, неизвестная модель, unsupported question и revocation tests. Успешные тесты показывают поведение только на данном наборе, не абсолютную защиту от любых атак. Правильный refusal считается успехом.

## 7. Provider и diagnostics

Offline-приёмка использует сменный LLMProvider и FakeLLMProvider. Следующий отдельный contract test проверяет OpenAI-compatible adapter на mock HTTP endpoint: schema, timeout/errors и конфигурацию LLM_BASE_URL/LLM_API_KEY/LLM_MODEL без provider-specific кода в retrieval. Настоящий cloud call для этой проверки не нужен. Переход на local endpoint сохраняет retrieval/index/metadata/API/evaluation; качество нового provider проверяется отдельно.

Diagnostic mode локальный и явно включаемый: candidates, ranks/scores по стадиям, selected context, answer/sources/reason_code. Raw question/context не становятся постоянными production-логами; секреты/PII не выводятся. Обычные логи сохраняют безопасные IDs/метрики/причины, согласно архитектуре. Scores не называются вероятностью истинности.

Нужна одна документированная команда проверки прототипа после отдельной установки locked dependencies; сетевой install не выдаётся за offline test. README содержит запуск и CLI-примеры. Тесты и evaluation отчёты с безопасными данными сохраняются в репозитории.

## 8. Связь с roadmap и текущие пробелы

Статус ниже зафиксирован 2026-11-05, после M1 merge и публикации PR #2; это не автоматическое закрытие критериев.

| Критерий | Этап | Состояние / недостающая проверка |
|---|---|---|
| Минимальный pipeline/Fake/refusal/citations | 1 | M1 слит; узкие fixture scenarios, не полный прототип |
| Source policy, ingestion, pages/units/provenance | 2 | Synthetic adapter в PR #2; real sample и полный набор ~10 документов не приняты |
| Snapshot/index и сохранение visibility/policy metadata | 3 | Следующий шаг; явных полей visibility в IngestedChunk пока нет, связь с registry есть |
| Hybrid search, Top-5, typos/paraphrases, diagnostics | 3–4 | Не реализованы; dataset нужен до оценки качества |
| Reranking quality / заменяемый adapter | 4 | Не реализованы; test interface не заменяет model benchmark |
| Полный grounded pipeline и негативные quality cases | 5 | M1 tests — частичное покрытие; ingestion output ещё не подключён к ответам |
| OpenAI-compatible HTTP contract, timeout/errors | 6 | Не реализован; отдельная mock проверка без cloud |
| 30 evaluation questions + воспроизводимый отчёт | Начинается до 4, расширяется на 7 | Не подготовлены; 46 существующих unit/integration tests не заменяют 30 вопросов |
| Одна команда полной приёмки и README | Сквозной | Команды отдельных проверок есть; общего prototype evaluation runner нет |
| Реальная документация/LLM и инженерная оценка | B + соответствующие этапы | Отдельный sample approval и quality gates; ничего не разрешено этой спецификацией |

Дальнейшая реализация сохраняет небольшие этапы roadmap, а не переносит весь прототип в одну задачу. Перед объявлением приёмки профиля должен быть опубликован фактический отчёт по его критериям и нерешённым ограничениям.
